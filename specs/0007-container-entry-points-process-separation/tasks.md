## Phase order

The user stories are ordered by dependency, not only by priority. Phase 2 builds what every story stands on: the core move under hosting contract version 2, the plane in the root, the control-plane root, rules contract version 5 in the rule source, the container library with its section, configuration roots, events, exit codes, and an entry point that validates before it binds and serves liveness. US3, readiness (Phase 3), comes first among the stories because the acceptance evidence of US1 reads readiness. US2, start-up refusal, the stop sequence, and the leases (Phase 4), needs Phase 3's readiness checks. US1 (Phase 5) adds telemetry, the two `Program.cs` files, the images, and the Compose acceptance topology. It is the acceptance criterion, and so the MVP checkpoint, though it lands third. US4, the migration command (Phase 6), needs Phase 2 and adds to the control plane's `Program.cs` from Phase 5. US5, the cross-host test (Phase 7), needs Phase 5's data-plane image. US6 (Phase 8) collects the seam's remaining evidence. Phase 9 publishes the documentation and runs the whole gate.

## Notes for every task

- **Restore on this PC**: Use the existing user-level proxy feed. Never commit a `nuget.config`, and never put that feed in a Dockerfile or CI. Export `DOTNET_ROOT` and `PATH` for the pinned SDK in `~/.dotnet` first.
- **Lock files**: After adding a project or changing a package or framework reference, run `dotnet restore Iskender.slnx --force-evaluate` and commit each changed `packages.lock.json`, since CI and the Dockerfiles restore in `--locked-mode` (rule B2). Package versions go only in `Directory.Packages.props` (rule B1).
- **Owning spec**: every new type in `PORTS`, `CORE`, `MGT`, and `CTR` has an XML comment naming ISK-0007 as its owning spec. Types moved into `CORE` keep their ISK-0006 owner and add ISK-0007 as the spec that moved them (HCON Ownership).
- **Moved-type rule (R1, US6.4, SC-009)**: in `HT` and `IT`, only lines that name a moved internal type may change: type and namespace names, constructor calls, and reflection on private fields. No assertion about observable behavior is changed or removed. If a behavior assertion fails after the move, the move is wrong; fix the code, not the test.
- **Failures are `GatewayException`s**: composition and the entry point throw only `new GatewayException(code)` with an existing registered code, and never attach an inner exception. Diagnostics name a layer and source name, a module, a feature, or a reason code, and never a configuration value, secret reference name, connection detail, file content, exception message, or request route value (CCON Diagnostics rule 6).
- **Host services**: Iskender never resolves `IConfiguration`, `IHostEnvironment`, or `IWebHostEnvironment` (HCON Registration rules 2, 3, 8). The entry point builds with `WebApplication.CreateEmptyBuilder` (R7).
- **Container validation**: every host or `ServiceCollection` a test or the entry point builds has `ValidateScopes` and `ValidateOnBuild` set to `true`.
- **Tests assert on codes**: assert on `ErrorCode`, exit codes, event IDs, diagnostics values, readiness reasons, and observed state, never on message text.
- **Container-runtime tests**: tests that need Docker call `RequireDocker()` (T014) or the linked `RequirePostgreSql()` first, so they are skipped with a reason locally without a container runtime, and fail when `CI=true` (CCON Test fixtures rule 4).
- **No fixed sleeps**: waits poll a state with ISK-0005's bounds and a timeout. A real flake is a blocker for `implement`, never a retry loop or a skip.
- **A failure you cannot fix**: report it. Never lower a count in SC-002 to SC-008, skip a test in CI, add a suppression, add a license to `check-license.sh`, or weaken a rule to get past it.

## Implementation Strategy

### MVP first

Phases 1 and 2, then US3 (Phase 3), US2 (Phase 4), and US1 (Phase 5). Stop and validate: the split containers launch in Compose, report live, and fail readiness with the reason that names the missing dependency, on 5 consecutive runs, with no value in any answer or log. That is this spec's acceptance criterion. US1 lands third because its evidence reads the readiness and stop behavior that US3 and US2 build.

### Incremental delivery

1. Setup and Foundational: the shared core, both roots, and an entry point that validates before it binds.
2. US3: readiness for every reason, with liveness never probing.
3. US2: start-up refusal, the stop sequence, and each plane's lease.
4. US1: telemetry, the entry points, the images, and the Compose acceptance (MVP).
5. US4: the migration command.
6. US5: the cross-host lifecycle test.
7. US6: the seam's remaining evidence.
8. Polish: the documentation, the quickstart, and the whole gate.

Each step leaves the build and every test passing, and is committed and pushed task by task.
