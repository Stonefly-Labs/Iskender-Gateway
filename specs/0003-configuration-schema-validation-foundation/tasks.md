# Tasks: ISK-0003 — Configuration Schema & Validation Foundation

**Input**: Design documents from `specs/0003-configuration-schema-validation-foundation/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, quickstart.md, contracts/configuration.md

**Tests**: Required. FR-035 and FR-036 ask for a negative fixture per error code and edge case and tests for every acceptance scenario, and SC-002 to SC-007 name test outcomes, so each task delivers its code and its tests together. Write the tests first and watch them fail, but commit only when the suite is green, because every commit must leave the build and tests passing (plan, "Implementation approach").

**Scope guard**: No CEL compiler, policy schema, plan, publication, activation, or reload; no secret store or resolver and no `ICredentialResolver`; no `AddIskender(...)` or other host wiring; no database table; no network call (FR-038). No new project under `src/` and no new project edge or role, so the ISK-0001 contract is not revised (FR-003). `Iskender.Providers.Abstractions` and `Iskender.Policy.Sdk` do not change (FR-034). Nothing changes under `.specify/`, `specs/0000-repo-bootstrap/`, `specs/0001-solution-dependency-boundaries-build-conventions/`, or in `.iskender/grounding.yaml`, and the ISK-0002 contract changes only in its error codes and versioning tables (FR-039, SC-008).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies on incomplete tasks)
- **[Story]**: Which user story the task belongs to (US1 to US5)
- Exact file paths are included in each description

## Path Conventions

`CC` means `src/Iskender.Core.Contracts`, `CFG` means `src/Iskender.Core.Contracts/Configuration`, `REG` means `src/Iskender.Domain/Registry`, `CCTests` means `tests/Iskender.Core.Contracts.Tests`, `DT` means `tests/Iskender.Domain.Tests`, `FX` means `tests/Iskender.Domain.Tests/Configuration/Fixtures`, and `Compat` means `tests/Iskender.Contracts.Compatibility.Tests`. Rules, forms, limits, codes, safe messages, templates, and event IDs come from `contracts/configuration.md` (version 1), type shapes from `data-model.md`, and design decisions from `research.md` (R1 to R18). Every type under `REG`, in any subfolder, is in the single namespace `Iskender.Domain.Registry` (ISK-0001 rules A17, A18).

## Phase order

The user stories are ordered by dependency, not only by priority. US1 is the named acceptance evidence and the MVP: it delivers the JSON path end to end, from document to report, snapshot, and revision. US2 adds YAML and the unsafe-value checks on that path, US3 proves section ownership and isolation on snapshots US1 creates, US4 adds environment variables and the overlay merge, and US5 adds the log events. After US1, US2, US3, and US5 can proceed in parallel. US4 touches the validator's entry point, so take it after US2.

## Notes for every task

- **Restore on this PC**: Use the existing user-level proxy feed. Never commit a `nuget.config` or put that feed in CI.
- **Lock files**: After adding a project or changing a package reference, run `dotnet restore Iskender.sln --force-evaluate` and commit each changed `packages.lock.json`, since CI restores in `--locked-mode` (ISK-0001 rule B2). Package versions go only in `Directory.Packages.props` (rule B1).
- **Version tags**: Every public type and member added in `CFG`, and every new `ErrorCodes` field, carries `[ContractVersion("core-contracts", 2)]` from the commit that adds it (FR-033). Regenerate `Compat/baselines/core-contracts.surface.txt` and `Compat/baselines/registries.json` in the same commit as any surface or registry change, so the harness passes on every commit.
- **No values in text**: No error, rendering, log event, exception message, or diagnostic holds a configuration value from any field. Build text from the code, the path, the schema, and the layer only (FR-020, TR-9).
- **Failures use codes**: Tests assert on the error code, path, and location, never on message text, except the rendering tests in US5 that check the documented form.
- **Fixtures**: Each negative fixture under `FX` has a sidecar `<name>.expect.json` holding `{ "errors": [ { "code", "path", "line", "column", "layer" } ] }` (FR-035). `.gitattributes` already keeps every text file LF, so line and column expectations hold on every platform.
- **A failure you cannot fix**: Report it. Never shrink a fixture, loosen SC-004's bound, add a suppression, or weaken a rule to get past it (plan, Risks).
