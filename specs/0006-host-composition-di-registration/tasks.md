## Phase order

The user stories are ordered by dependency, not only by priority. Phase 2 builds what every story stands on: the error codes, rules contract version 4 with `Iskender.Hosting` as a public contract, the composition seam, `AddIskender(...)` with its options, once-per-container validation, the start-up service, the diagnostics, and the fixture library. US1, composition in process, is the MVP (Phase 3): the infrastructure registrations, the sample without its Iskender route group, and the embedded composition acceptance group. US2's refusal group (Phase 4) needs only Phase 2, and can run beside Phase 3. US3 (Phase 5) adds `MapIskender(...)` and the request bootstrap, and maps the group in the sample. US4 (Phase 6) needs the bootstrap for its concurrency test and every registration for its lifetime matrix. US5 (Phase 7) checks every registration mistake across all of them. Phase 8 publishes the documentation and runs the whole gate.

## Notes for every task

- **Restore on this PC**: Use the existing user-level proxy feed. Never commit a `nuget.config` or put that feed in CI. Export `DOTNET_ROOT` and `PATH` for the pinned SDK in `~/.dotnet` first.
- **Lock files**: After adding a project or changing a package or framework reference, run `dotnet restore Iskender.slnx --force-evaluate` and commit each changed `packages.lock.json`, since CI restores in `--locked-mode` (ISK-0001 rule B2). Package versions go only in `Directory.Packages.props` (rule B1).
- **Version tags**: every new `ErrorCodes` field carries `[ContractVersion("core-contracts", 5)]`, and every public type of `HST` carries `[ContractVersion("hosting", 1)]`, from the commit that adds it. Regenerate `Compat/baselines/core-contracts.surface.txt`, `Compat/baselines/registries.json`, and `Compat/baselines/hosting.surface.txt` in the same commit as any surface or registry change.
- **No `Iskender.Domain` type on the surface**: no public member of `HST` names a type from `Iskender.Domain`, including in a generic argument, a delegate signature, or an attribute (FR-018).
- **Owning spec**: every new type in `PORTS`, `HST`, `INF/Composition`, and the new files in `INF/Coordination`, `PG`, and `RD` has an XML comment naming ISK-0006 as its owning spec (HCON Ownership rule 4).
- **Failures are `GatewayException`s**: registrations and start-up throw only `new GatewayException(code)` with a registered code. Diagnostics name a module, a layer and source name, or a coordinator kind and primitive, and never a configuration value, secret reference name, connection detail, file content, exception text, or request route value (HCON Diagnostics rule 2). Never attach an inner exception.
- **Host services**: Iskender never resolves `IConfiguration`, `IHostEnvironment`, or `IWebHostEnvironment`, never registers `TimeProvider`, `ILoggerFactory`, or a credential provider, and resolves those it uses with `GetService`, falling back to `TimeProvider.System`, `NullLoggerFactory`, and a `null` provider (HCON Registration rule 8).
- **Container validation**: every host a test builds has `ValidateScopes` and `ValidateOnBuild` set to `true`. The fixture sets both, and a test that builds a host itself sets both.
- **Tests assert on codes**: assert on the `ErrorCode`, event IDs, diagnostics values, and observed state, never on message text.
- **Container tests**: the single-instance lease test calls `RequirePostgreSql()` first, so it is skipped with a reason locally without a container runtime, and fails when `CI=true`. No other hosting test needs a container (HCON Test fixture rule 3).
- **A failure you cannot fix**: report it. Never lower a count in SC-002, SC-003, or SC-006, skip a test in CI, add a suppression, list a static field that holds state, or weaken a rule to get past it.
