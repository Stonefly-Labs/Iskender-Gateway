# Tasks: ISK-0005 — Coordination & Redis Capability Contracts

**Input**: Design documents from `specs/0005-coordination-redis-capability-contracts/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, quickstart.md, contracts/coordination.md, contracts/persistence.md (version 2)

**Tests**: Required. FR-030 names the refusal tests (User Story 1) and the lease fencing tests (User Story 2) as acceptance evidence, FR-029 requires a conformance suite against every implementation, and SC-002 to SC-007 name test outcomes, so each task delivers its code and its tests together. Write the tests first and watch them fail, but commit only when the suite is green, because every commit must leave the build and tests passing (plan, "Implementation approach").

**Scope guard**: No rate algorithm, quota window, budget, breaker, worker, or outbox; no `AddIskender(...)` or other host wiring, readiness endpoint, or start-up failure mapping; no code that starts the single-instance guard outside tests; no `ICoordinationCredentialProvider` or secret reader outside test projects; no session-scoped lock and no use of `IUnitOfWork.AcquireAdvisoryLockAsync` or any advisory lock by leases or the fencing guard; no PostgreSQL table outside `isk_coordination`; no cloud SDK; no Local Compose Redis (SC-008). No change under `.specify/`, to `.iskender/grounding.yaml`, to the ISK-0001 rules contract or its rule source, or to `Iskender.Providers.Abstractions` or `Iskender.Policy.Sdk`. The ISK-0002 contract changes only in its error codes and versioning tables. The persistence contract's Advisory locks section stays byte-for-byte identical to version 1.

## Phase order

The user stories are ordered by dependency, not only by priority. Phase 2 builds everything every story stands on: the ports, error codes, the section, diagnostics, the conformance library, persistence contract version 2 in code with the `coordination` migration, and the Redis project, fixture, connection, and classifier. US1's capability check and gate come next (Phase 3) and are the MVP, testable with fake ports. US2 (leases and fencing, Phase 4) provides the PostgreSQL lease that US1's single-instance verification needs, so that part of US1 follows as Phase 5. US3 (counters), US4 (cache), and US5 (health and canaries) follow. Both acceptance groups pass at the end of Phase 5.

## Notes for every task

- **Restore on this PC**: Use the existing user-level proxy feed. Never commit a `nuget.config` or put that feed in CI. Export `DOTNET_ROOT` and `PATH` for the pinned SDK in `~/.dotnet` first.
- **Lock files**: After adding a project or changing a package reference, run `dotnet restore Iskender.slnx --force-evaluate` and commit each changed `packages.lock.json`, since CI restores in `--locked-mode` (ISK-0001 rule B2). Package versions go only in `Directory.Packages.props` (rule B1).
- **Version tags**: every new `ErrorCodes` field carries `[ContractVersion("core-contracts", 4)]` from the commit that adds it. Regenerate `Compat/baselines/core-contracts.surface.txt` and `Compat/baselines/registries.json` in the same commit as any surface or registry change.
- **Owning spec**: every new type in `PORTS`, `INF`, `PGC`, and `RD` has an XML comment naming ISK-0005 as its owning spec (FR-001, contract Ownership rule 4).
- **Failures are `GatewayException`s**: ports throw only `new GatewayException(code)` with a registered code, setting the `ErrorDiagnostics` values `failure_class` and, for a write whose outcome is unknown, `outcome = unknown` (contract Failures rule 1). Never attach an inner exception, key, hash, host, or server text. Contention and a denied reservation are results, never exceptions.
- **Scope before I/O**: every port method checks its `CoordinationScope`, name, durations, expiry, amounts, and value size before any I/O, and the deadline and cancellation before any I/O (spec Edge Cases).
- **Nothing sensitive in text**: no log field, metric label, activity tag, exception message, health result, or `ToString()` holds a scope ID, derived key, hash, cached value, host, port, user name, password, connection text, or server error text (FR-026). Labels are limited to the contract's Diagnostics list.
- **Tests assert on codes**: assert on the `ErrorCode`, failure class, reason, grant counts, tokens, and stored state, never on message text.
- **Container tests**: every test that needs PostgreSQL calls `RequirePostgreSql()` first, and every test that needs Redis calls `RequireRedis()` first, so it is skipped with a reason locally without a container runtime, and fails when `CI=true` (FR-031).
- **Concurrency tests**: start contenders behind a barrier and assert on final state and recorded tokens, never on timing (plan, Risks). Expiry tests on the local substitutes use a fake `TimeProvider`. Distributed expiry tests use durations within `leases.minimumDuration` and wait on observed expiry with generous bounds.
- **A failure you cannot fix**: report it. Never lower a count in SC-002 to SC-004, skip a container test in CI, add a suppression, raise a declared consistency level to pass a check, or weaken a rule to get past it.
